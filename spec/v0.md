# Lantern Zero protocol, v0 (draft)

**Status:** draft, unstable. Anything in v0 may change without notice. The
first stable version will be `v1`.

This document defines the connection URL, the transport, and the HTTP API
used between wallets, Lantern Zero servers, relays, and push gateways. The key
words MUST, MUST NOT, SHOULD, and MAY are used as in RFC 2119.

## 1. Roles and trust

| Role | Holds | Learns |
| --- | --- | --- |
| **Wallet** (client core inside a wallet app) | spending keys, account token | everything about its own funds |
| **Relay** (OHTTP relay, run by a third party) | nothing | client IP, request sizes and timing |
| **Server** (Lantern Zero) | account token hashes, push subscriptions, leased viewing keys (RAM only) | that an account exists; in scanning mode, incoming payments during the lease |
| **Push gateway** (run by the wallet vendor) | APNs/FCM credentials | device push tokens, push timing |
| **Apple / Google** | — | push timing |

### 1.1 Relays

- The relay SHOULD be run by a third party: neither the server operator nor
  the wallet vendor. It MUST NOT be run by the server operator.
- Server operators MUST NOT choose relays for their users. The wallet
  vendor ships the relay list in the wallet, and users MAY edit it. This
  repository keeps a community list (`spec/relays.md`) as a starting point;
  it is not authoritative.
- Wallets SHOULD configure at least two relays and pick one at random for
  each request, so that no single relay sees all of a user's traffic.

### 1.2 Trust limits

These limits are inherent to the design, and wallets SHOULD explain them to
users:

- **Collusion.** If the relay and the server collude, they can link a
  client's IP address to its account. If one party runs the server, the
  gateway, and the relay, it learns everything any of them would.
- **Scanning mode.** While a lease is active, the server operator can see the
  user's incoming payments (and, with spend alerts, outgoing ones).
- **Payment-push timing.** With instant alerts (5.2), the gateway and
  Apple/Google can see that a device received a push outside the wake
  schedule. That suggests the device is in scanning mode and got paid at that
  moment. Governments can obtain push records with legal process.
- **Small anonymity sets.** The wire protections in 3.2 and 4.3 hide a user
  among the server's other users. On a server with few users, they hide
  little.
- **Your own light wallet server.** Wallets still download blocks from a
  lightwalletd or Zaino server of their choosing. That server sees the
  wallet's IP address and which heights it fetches (see 6.3).

## 2. Connection URL

A user connects a wallet by pasting or scanning one URL:

```
lanternzero://<host>[:<port>][/<base-path>]#<account-token>
```

- The scheme implies HTTPS to `https://<host>[:<port>][/<base-path>]` (the
  **base URL**). Servers MUST NOT require plain HTTP.
- Self-hosted servers MAY instead be given as a Tor onion address
  (`lanternzero://<name>.onion/...`); see 3.1. For `.onion` hosts the base
  URL is `http://`: Tor already encrypts and authenticates the connection to
  the onion address, and onion services rarely have TLS certificates.
- Wallets MUST match the scheme case-insensitively (RFC 3986 §3.1). Phone
  keyboards often capitalize the first letter of a pasted URL.
- The **account token** sits in the fragment. The wallet MUST strip it before
  using the base URL anywhere, and MUST NOT log it.
- Wallets MUST mask the token in their UI (show only the last four
  characters) and SHOULD keep it in the platform keychain.
- Hosted, self-hosted, and wallet-sponsored servers all use this format.

### 2.1 Handing the URL to a wallet

Any app can register a custom scheme such as `lanternzero://`. If the user
taps a link with that scheme, another app may capture the token along with
it. Therefore:

- Wallets MUST accept the URL by paste and by QR scan. These are the
  recommended paths.
- Wallets MUST NOT rely on being opened by `lanternzero://` links. To open
  from a link, use iOS universal links or Android app links on an `https` URL
  with the same fragment.
- A page served at an `https` form of the URL (for example, a landing page
  shown when no wallet is installed) MUST NOT load third-party scripts,
  because scripts can read the fragment. It SHOULD set
  `Referrer-Policy: no-referrer`.

### 2.2 Account token

```
lzt_<base64url( 32 random bytes || CRC-32 of those bytes )>
```

That is 36 bytes, unpadded base64url: 48 characters after the prefix, 52 in
total.

- The CRC-32 is the IEEE 802.3 variant (as in zlib and PNG), appended
  big-endian.
- The CRC-32 lets wallets catch typos and lets secret scanners match tokens
  with few false positives. It adds no security.
- The token is a bearer secret (invariant 6). After issuance it travels only
  inside OHTTP-encapsulated requests (or Tor, 3.1), in
  `Authorization: Bearer <token>`.
- Servers store only `SHA-256(token)`, compare in constant time, and never
  log the token or its hash.
- The `lzt_` prefix is intended for registration with GitHub secret scanning.

### 2.3 Issuance

Sign-up and payment are outside this spec, but whoever issues tokens MUST
keep the token itself away from the issuing server:

- The token MUST be generated on the user's device: in the browser for web
  sign-up (Web Crypto `getRandomValues`), or by the self-host installer. The
  issuer receives only `SHA-256(token)`.
- The sign-up page then builds the connection URL locally and shows it as
  text and a QR code. It MUST NOT send the token anywhere.
- Rotation and deletion use the API (4.6), not a website.

## 3. Transport

### 3.1 Oblivious HTTP

Every request from a wallet (or merchant backend) to a server MUST use
Oblivious HTTP (RFC 9458) through a relay (1.1). The inner message is Binary
HTTP (RFC 9292).

- **Tor exception.** A self-hosted server MAY instead be reached directly
  over a Tor onion service, with no OHTTP. One user per server leaves
  nothing to hide among, and Tor already hides the IP address. Hosted and
  wallet-sponsored servers MUST use OHTTP.
- **Origin.** The OHTTP gateway lives at the server's origin, not under the
  base path, as RFC 8615 requires for well-known URIs. The inner request's
  target is the full base URL plus the API path.
- **Key configuration.** The server publishes its key configuration at
  `GET https://<host>/.well-known/ohttp-gateway` (RFC 9540). Wallets SHOULD
  fetch it through a relay, not directly.
- **Encapsulated requests** go to
  `POST https://<host>/.well-known/ohttp-gateway` as `message/ohttp-req`.
- **Relay opt-in.** Some relays forward only to gateways that declare a
  purpose they accept. Servers MUST answer
  `GET https://<host>/.well-known/ohttp-gateway?allowed_purposes` with
  content type `application/x-ohttp-allowed-purposes`. The body is the
  ALPN-style encoded list containing exactly one purpose string:
  `LanternZero v0 4bca76ac-1094-4330-97df-03d5c81b576d`. Servers MUST NOT
  claim any other protocol's purpose, such as BIP77.
- Servers MUST reject requests to the API paths in section 4 that arrive
  without OHTTP, except over the Tor exception above.

### 3.2 Key consistency

A server could give each user a different key configuration and use it to
tag them. No IETF mechanism for this is standardized: the drafts
(`draft-ietf-privacypass-consistency-mirror`, `draft-schwartz-ohai-consistency-doublecheck`)
have expired. v0 uses a simple version of the double-check approach:

- Servers MUST serve the same key configuration to everyone. They SHOULD
  rotate it no more than once a week, and SHOULD publish the current
  configuration's SHA-256 in `info` (4.7) and in their release notes.
- Wallets MUST fetch the key configuration through two different relays and
  refuse to use it unless both copies match.
- Wallets SHOULD cache it, and repeat the two-relay check when it changes.

### 3.3 Uniform sizes (invariant 4)

A relay sees only sizes and timing. Neither may reveal a user's mode.

- Every inner request MUST be padded with Binary HTTP padding to exactly
  **4096 bytes**. A request that does not fit is a protocol error.
- Every inner response MUST be padded to exactly **4096 bytes**. Content
  that does not fit is split into pages (`next` cursor), and each page is
  padded the same way.
- In both modes the wallet MUST make the same requests on the same schedule:
  - one `wake` (4.2) per wake, never more;
  - a continuous `events` long-poll (4.3) while the app is in the foreground;
  - no other requests, except rare account actions (4.1, 4.6, 4.7) and
    fetches of the `next` page (4.3).

  Default-mode wallets send `lease: null` and long-poll exactly as scanning
  wallets do.
- Wallets MUST NOT send extra requests in response to a payment push (5.2).
  The push itself carries what the wallet needs to show an alert.

**Bandwidth.** 4096 bytes fits a full lease request (4.2) and a typical
event. A foreground wallet long-polling about every 25 s moves about
600 KB an hour in each direction. At 10k users with 10% in the foreground,
the server sends about 420 GB a month.

### 3.4 Replay protection

OHTTP does not stop a relay from resending a captured request (RFC 9458
§6.5). Replaying an old `wake` could restart a lease the user has ended.
Therefore:

- Every inner request MUST carry a `Date` header. Servers MUST reject
  requests whose `Date` differs from the server's clock by more than
  60 seconds.
- Every authenticated request body MUST carry `seq`: an integer chosen by
  the sender that increases on every request.
- **Windows.** The server keeps a window of the 64 most recent values, up to
  and including the highest accepted `seq` (as in IPsec and DTLS):
  - for requests that name a `device_id`, one window per device;
  - for requests that don't (webhook, token, and account calls, often sent
    by a merchant backend with no device), one window per account.

  It MUST reject a `seq` that falls below the window or that it has already
  seen.
- **Choosing `seq`.** Senders SHOULD use the current Unix time in
  milliseconds, or one more than the last value sent if the clock hasn't
  passed it. Values then keep rising even after app storage is wiped or
  restored from an old backup.
- **Recovery.** A rejected `seq` gets `409` with problem type `stale-seq`
  and a `min_seq` member: the lowest value the server would accept now. The
  sender retries once with a `seq` of at least `min_seq`.
- Servers MAY store `seq` state on disk. It contains no key material.

### 3.5 Rate limits

OHTTP hides client IPs from the server, so servers cannot rate-limit by IP.

- Servers MUST rate-limit per account and per device, and return `429` with
  `Retry-After`.
- Relays SHOULD rate-limit per client IP.

### 3.6 Errors

Errors use Problem Details (RFC 9457), `application/problem+json`, with
`type` values under `https://lanternzero.com/problems/`.

## 4. API

All paths are relative to the base URL and live under `/v0/`.

- Except for `info`, requests carry `Authorization: Bearer <token>`.
- Bodies are JSON, and clients MUST ignore unknown fields.
- Heights and amounts are integers, and amounts are in zatoshis.
- Binary values are unpadded base64url. Times are RFC 3339 in UTC.

### 4.1 `POST /v0/devices`: register for wake-ups

The body is a Web Push subscription, the same shape as the W3C
`PushSubscription`:

```json
{
  "seq": 1,
  "endpoint": "https://push.examplewallet.app/wp/<opaque>",
  "keys": {
    "p256dh": "<RFC 8291 receiver public key>",
    "auth": "<RFC 8291 auth secret, 16 bytes>"
  }
}
```

- `endpoint` is an RFC 8030 push resource on the wallet vendor's gateway:
  an `https` URL of at most 1024 bytes, with no user name or password.
- **SSRF.** The server connects to whatever endpoint a wallet registers, so
  hosted servers MUST apply the same address rules as for webhooks (4.5).
  They SHOULD also accept only gateway hosts on an allow-list of known
  wallet vendors.
- **Limit.** Servers MUST cap devices per account (default 10), so one
  account can't aim a ping fan-out at someone else's host.
- The gateway SHOULD encrypt the APNs or FCM device token into the
  `<opaque>` part with the gateway's own key, so the server never sees the
  raw device token.
- Android wallets MAY register a UnifiedPush endpoint instead, so users
  without Google services get pushes. The distributor must support
  RFC 8291 `aes128gcm`.
- Response `201`: `{ "device_id": "<id>" }`. Registering the same `endpoint`
  again replaces the old record.
- The first request from a new device sets that device's `seq` baseline
  (3.4).
- `DELETE /v0/devices/{device_id}` (body `{ "seq": n }`) unregisters a
  device.

### 4.2 `POST /v0/wake`: the per-wake request

The wallet sends exactly one `wake` each time it wakes, in both modes.

```json
{
  "device_id": "<id>",
  "seq": 42,
  "ack": ["<event id>"],
  "lease": null
}
```

or, to start or renew a lease:

```json
{
  "device_id": "<id>",
  "seq": 42,
  "ack": [],
  "lease": {
    "keys": ["uivk1…"],
    "from_height": 3500000,
    "duration_secs": 604800,
    "spend_alerts": false,
    "alert_mode": "instant"
  }
}
```

- **`ack`** lists events the wallet has processed (4.4). It is always
  present, even when empty.
- **`keys`** holds 1 to 4 Unified Incoming Viewing Keys (ZIP 316), all for
  one account.
  - Unified Full Viewing Keys (`uview1…`) are accepted **only** when
    `spend_alerts` is `true`. The wallet MUST NOT send a full viewing key
    unless the user explicitly turned spend alerts on.
  - There is no separate Ironwood key. The Orchard item covers both the
    Orchard and Ironwood pools, because one Orchard-protocol IVK
    trial-decrypts both (ZIP 229, ZIP 326).
  - That IVK depends on the account's `use_qsk` setting (ZIP 326). A wallet
    that does not know its account's setting (for example, just after
    restoring from seed) MAY send one key for each variant. That is why
    `keys` is a list.
  - Servers MUST accept both ZIP 316 Revision 0 and Revision 2 encodings,
    in all-lowercase or all-uppercase form (Bech32m; QR codes often use
    uppercase). Mixed case is invalid.
  - The keys in one lease MUST be distinct.
- **Re-sending.** The wallet re-sends the keys on every wake. This keeps
  request sizes the same in both modes, and lets a lease recover at the next
  wake after a server restart.
- **`from_height`** SHOULD be the wallet's last fully scanned height, so the
  scanner covers any gap since the last wake. The server MAY clamp it to at
  most 7 days before the tip; it does not scan older history.
- **`duration_secs`** is clamped to `[86400, 604800]` (24 h to 7 days), and
  also to the end of the account's paid period. Wallets SHOULD request
  604800: iOS throttles background pushes, so shorter leases can lapse
  between wakes.
- **`alert_mode`** is `instant` or `private`; see 5.2.
- **`lease: null`** ends any active lease on the account at once (opt-out).
  A default-mode wallet sends `null` on every wake.
- **Unknown device.** If the server no longer knows `device_id` (for
  example, after the gateway reported the subscription gone), it answers
  `404` with problem type `unknown-device`. The wallet then registers again
  (4.1).
- **No scanning.** A server that doesn't offer scanning answers a lease with
  `501` and problem type `scanning-unavailable`, and drops the keys at once.
  A server that scans but doesn't offer spend alerts answers a lease with
  `spend_alerts: true` the same way, with problem type
  `spend-alerts-unavailable`.
- **Backfill.** For a new lease, the server scans from `from_height` (as
  clamped) up to the tip, then follows new blocks. Payments found while
  scanning back don't trigger instant pushes (5.2): the wallet is awake and
  gets them from this response, the next `wake`, or the long-poll.

Response `200`:

```json
{
  "tip": 3512345,
  "lease": { "active": true, "expires_at": "2026-11-07T12:00:00Z" },
  "hints": [ { "start": 3511020, "end": 3511021 } ],
  "events": [ ],
  "cursor": "<opaque>",
  "next": null
}
```

- **`tip`** is the height of the best block the server knows, or `0` while
  it has not yet reached its chain source (for example, just after
  starting).
- **`hints`** are half-open height ranges `[start, end)` that hold notes for
  unacknowledged mined events.
  - They map onto librustzcash `ScanPriority::FoundNote`. See 6.3 for how
    wallets must use them.
  - Hints are dropped when their events are acknowledged or expire.
  - They are empty when no lease is active.
- **`events`** holds the account's unacknowledged events (4.3), oldest
  update first, as many as fit in the fixed response size (3.3).
- **`cursor`** is where the wallet's long-poll starts.
- **`next`** is `null`, or a cursor for the events that didn't fit. The
  wallet fetches them with `POST /v0/events`, `cursor` set to `next`, and
  `wait: 0`.
- An event whose `compact_tx` alone doesn't fit in a page is sent without
  it. The wallet finds the transaction in its normal sync, at the hinted
  height.

### 4.3 `POST /v0/events`: long-poll

```json
{
  "device_id": "<id>",
  "seq": 43,
  "cursor": "<opaque>",
  "wait": 25,
  "ack": []
}
```

- The server holds the request, **even if the account already has events
  newer than `cursor`**, until the next release (below) or until `wait`
  runs out, then returns the events newer than `cursor`. The server clamps
  `wait` to 25–30 s.
- **`wait: 0`** returns at once. Wallets MUST use it only to fetch a `next`
  page (4.2), never as their regular poll.

**Release rule (invariant 4).** An early return would show the relay that
this user scans, or just got a payment. So the server MUST NOT release one
waiting poll early on its own. It releases **every** waiting poll, for all accounts,
when either of these happens:

- a new block arrives, or
- any lease on the server matches a transaction.

Each poll is released after its own random delay of 0–2 s. A poll that
waits the full time returns an empty list.

Response `200`:

```json
{
  "cursor": "<opaque>",
  "events": [
    {
      "id": "<id>",
      "rev": 1,
      "kind": "received",
      "status": "mempool",
      "height": null,
      "confirmations": 0,
      "compact_tx": "<CompactTx protobuf bytes>"
    }
  ],
  "next": null
}
```

- `kind` is `received` or, with spend alerts, `spent`.
- `status` is one of:
  - `mempool`: seen but not yet mined;
  - `mined`: carries `height` and `confirmations`;
  - `reorged`: the block that held the transaction left the best chain.
    The event moves back to `mempool`, or to `mined` at a new height, when
    the transaction is seen again.
- The server updates an unacknowledged event in place and increments `rev`
  each time its status or confirmations change. Updates stop once
  `confirmations` reaches the server's finality depth, which `info` reports
  (4.7).
- The event carries the `CompactTx` so the wallet can trial-decrypt it
  itself, without looking the transaction up anywhere (invariant 7).

### 4.4 Events: scope, acknowledgement, storage

- Events belong to the **account**, not the device. Each device tracks its
  own `cursor`.
- An `ack` from any device deletes the event (and its hints) for the whole
  account at once. Other devices of the account still find the payment by
  scanning normally.
- Unacknowledged events are deleted 7 days after creation (invariant 3).
- Events and hints live **only in server memory**, like keys. A restart
  drops them. When the wallet re-establishes its lease from `from_height`,
  the scanner finds the same transactions again.
- An event's `id` is deterministic, so a re-detected transaction keeps its
  id and wallets and webhook receivers can deduplicate:

  ```
  id = base64url( HMAC-SHA256( server_secret,
         account_id || txid || pool || index )[0..16] )
  ```

  | Field | Encoding |
  | --- | --- |
  | `account_id` | 16 random bytes the server assigns at account creation; never derived from the token, so rotation keeps it |
  | `txid` | 32 bytes, in the transaction hash's internal byte order |
  | `pool` | 1 byte: `0` Sapling, `1` Orchard, `2` Ironwood |
  | `index` | 4 bytes big-endian: the output's (Sapling) or action's (Orchard, Ironwood) index within its bundle |
  | `server_secret` | at least 32 random bytes, kept for the server's lifetime |

### 4.5 Webhooks (merchants and self-hosters)

Webhooks are not for phones. A merchant backend configures one over OHTTP
like any other client:

```
PUT /v0/webhook
{ "seq": 7, "url": "https://shop.example/hooks/zec" }
```

Response `200` returns the signing secret **once**:

```json
{ "secret": "whsec_<base64 of 32 random bytes>" }
```

- The server generates the secret; the client never supplies it. A new
  `PUT` replaces both the URL and the secret.
- Deliveries follow Standard Webhooks:
  - headers `webhook-id` (the event `id` plus `rev`), `webhook-timestamp`,
    and `webhook-signature` (`v1,` + HMAC-SHA256);
  - retries back off over 24 hours, after which the delivery is dropped;
  - receivers deduplicate on `webhook-id`.
- The delivery body is the event from 4.3, plus decrypted fields a merchant
  needs:

  ```json
  {
    "…": "fields from 4.3",
    "txid": "<hex>",
    "pool": "ironwood",
    "amount": 150000000,
    "memo": "<base64url, or null>"
  }
  ```

  `pool` is `sapling`, `orchard`, or `ironwood`. The delivery goes to the
  merchant's own endpoint over TLS, outside OHTTP. Invariant 5 governs push
  payloads, not webhooks.
- **SSRF.** Hosted servers MUST reject webhook URLs that are not `https`, or
  that resolve to loopback, private, link-local, or unique-local addresses.
  They MUST check again at connect time, to defeat DNS rebinding. Self-hosted
  servers MAY allow private targets through a configuration flag.
- Pending deliveries are held in memory, like events (4.4).
- `DELETE /v0/webhook` (body `{ "seq": n }`) removes the webhook.

### 4.6 Account lifecycle

- `POST /v0/token/rotate` (body `{ "seq": n, "new_token_hash": "<SHA-256>" }`)
  replaces the token.
  - The wallet generates the new token itself and sends only its hash, as at
    issuance (2.3).
  - The old token keeps working until the new one is first used, or for
    24 hours, whichever comes first. A lost response then can't lock the
    user out.
  - The wallet SHOULD show the user a new connection URL.
- `DELETE /v0/account` (body `{ "seq": n }`) immediately drops the account's
  leases, events, hints, devices, webhook, and token hash.

### 4.7 `POST /v0/info`

Sent over OHTTP with no auth. Response:

```json
{
  "versions": ["v0"],
  "network": "main",
  "wake_interval_secs": 1800,
  "long_poll_wait_secs": [25, 30],
  "finality_depth": 10,
  "vapid_public_key": "<P-256 public key, base64url>",
  "ohttp_key_config_sha256": "<hex>",
  "attestation": null
}
```

- Wallets MUST check that `network` (`main`, `test`, or `regtest`) matches
  their own network, and MUST refuse to connect otherwise.
- `attestation` is reserved for scanning inside an attested enclave. It is
  always `null` in v0. A later version will define it, and wallets that
  require attestation will send keys only to servers that provide it.

## 5. Push

### 5.1 Scheduled wake-ups

- Every **30 minutes** the server sends a ping to every registered device.
- Each device's ping goes out at a random time within the first 5 minutes
  of the slot, chosen fresh each slot. This spreads the load on the server
  and on light wallet servers. The spread is the same in both modes.
- The ping plaintext is JSON, padded with spaces to exactly **1024 bytes**,
  then encrypted to the device with RFC 8291 (`aes128gcm`):

  ```json
  {"v":0,"t":"wake","events":[]}
  ```

- `events` is empty, except under `private` alerts (5.2). Because the size is
  fixed, the gateway and Apple/Google cannot tell the two apart.

### 5.2 Payment alerts in scanning mode

The lease's `alert_mode` picks one of two behaviors:

| | `instant` | `private` |
| --- | --- | --- |
| How the alert arrives | an extra push as soon as a lease matches | inside the next scheduled ping |
| Alert delay | seconds | up to about 35 minutes |
| What the gateway and Apple/Google learn | when the user got paid | nothing beyond the schedule |

- **`instant`** is the default, because it is why users opt in. The server
  sends an extra push whose plaintext is
  `{"v":0,"t":"payment","events":[<event>]}`. The event is the one from 4.3
  without `compact_tx`. The plaintext is padded to 1024 bytes and
  RFC 8291-encrypted (invariant 5).
- **`private`** places up to 4 such events in the next scheduled ping's
  `events`.
- In both modes, the wallet decrypts on the device and shows a local alert.
  It MUST NOT make an off-schedule request because of the push (3.3). Full
  details arrive on the next scheduled `wake`, or on the long-poll once the
  user opens the app.
- Wallets MUST offer both modes on the consent screen (6.3).
- **Cover pushes are not used.** Apple advises at most 2–3 background
  pushes an hour, and the 30-minute schedule already uses most of that
  budget. On iOS, a decoy visible push can't be suppressed without Apple's
  notification-filtering entitlement, so users would see it.

### 5.3 Server → gateway (RFC 8030 and RFC 8292)

The server delivers to the device's `endpoint` with a standard Web Push
request:

```
POST <endpoint>
Content-Encoding: aes128gcm
TTL: 1800
Urgency: normal
Topic: wake
Authorization: vapid t=<JWT>, k=<server VAPID public key>

<RFC 8291 ciphertext>
```

| | Scheduled wake | Instant payment push |
| --- | --- | --- |
| `Urgency` | `normal` | `high` |
| `TTL` | `1800` (useless after the next slot) | `86400` |
| `Topic` | `wake` (so an offline device gets only the latest ping) | none |

- **Authentication.** The server signs a VAPID JWT (RFC 8292) with the key
  published in `info`. Gateways MUST verify it. They SHOULD accept only an
  allow-list of server keys, or rate-limit per key, so the gateway can't be
  used to send spam.
- `404` or `410` means the subscription is gone; the server MUST delete
  that device record.
- `429` means the server MUST wait at least `Retry-After`.
- **Topic and `private` alerts.** Under `private` alerts, a newer wake ping
  replaces an older one that is still pending. The server MUST therefore
  carry any unacknowledged events forward into each new ping until the
  wallet acknowledges them.

### 5.4 Platform mapping (gateway guidance)

| | Scheduled wake | Instant payment push |
| --- | --- | --- |
| **APNs** | `apns-push-type: background`, `apns-priority: 5`, `content-available: 1`, `apns-collapse-id` from `Topic` | `apns-push-type: alert`, `mutable-content: 1`, generic visible text (for example "New activity"); a Notification Service Extension decrypts the real content on the device |
| **FCM** | data message, `priority: normal`, `collapse_key` from `Topic` | data message, `priority: high`; the app MUST show a visible notification, or Android will demote the app's later high-priority messages |

- The visible text that Apple or Google relay MUST NOT include amounts,
  memos, or txids.
- iOS throttles background pushes and does not guarantee delivery. Wallets
  MUST work correctly when wakes are missed.

## 6. Obligations

### 6.1 Server invariants

- Viewing keys stay in scanner memory only (6.2). A restart drops them, and
  wallets re-send them at their next `wake`.
- Leases end at expiry, on `lease: null`, on account deletion, or when the
  paid period ends, whichever comes first.
- Events, hints, and pending webhook deliveries also live in memory only, and
  are kept for at most 7 days. The server keeps no per-key history.
- The scanner never makes per-transaction chain lookups (`GetTransaction`).
  It reads blocks and the mempool in bulk only.

### 6.2 Server memory hygiene

"Never on disk" includes swap and crash dumps. Servers MUST:

- **Swap:** lock memory that holds keys and key-derived data (`mlock`), or
  run with swap turned off or encrypted.
- **Core dumps:** turn them off for the scanner process (`RLIMIT_CORE=0`,
  and `PR_SET_DUMPABLE=0` on Linux).
- **Wiping:** keep keys in types that zero their memory on drop (for example
  `secrecy` or `zeroize`), and parse keys straight into those types.
- **Printing:** give key types no `Debug` or `Display` output that shows
  content, and keep keys out of panic messages, error strings, and metric
  labels.

### 6.3 Wallet obligations

- **Consent.** Before the first lease, the wallet MUST show a consent
  screen. It must state that:
  - the operator, anyone who breaches it, and anyone who compels it can see
    incoming payments for the key while the lease lasts;
  - with `instant` alerts, Apple or Google can see when payments arrive;
  - a dedicated receiving account limits what the key reveals, and is
    recommended.
- **Hints.** Fetching only the hinted heights from a light wallet server
  would show that server where the user's notes are. Therefore:
  - wallets MUST NOT fetch hinted heights, or their tree states, on their
    own;
  - wallets SHOULD use hints only to reorder ranges within their normal
    sync, which covers every block from the last scanned height to the tip;
  - if a wallet must fetch a hinted range out of order, it MUST do so over
    Tor or OHTTP, with that range inside a wider one.
- **Transactions.** Wallets SHOULD use the `compact_tx` in events, and
  SHOULD NOT call `GetTransaction` for an event's txid.

## 7. Versioning and process

- The path prefix (`/v0/`) carries the major version. v0 has no
  compatibility promises.
- From `v1`, changes within a major version are additive only.
- **Test vectors** for tokens, event ids, the replay window, lease
  durations, and ping padding are in `spec/vectors/v0.json`. The
  `lz-proto` crate's tests fail if the vectors and the code disagree.
- **Still to add:** JSON Schemas for every body (`spec/schemas/`), and
  vectors for RFC 8291 payloads and padded Binary HTTP messages.
- Once v1 is stable, the protocol may be proposed as a ZIP through the light
  client working group.

## 8. Decisions on earlier open questions

| Question | Decision | Why |
| --- | --- | --- |
| Ironwood key encoding | No separate key. The Orchard item in a UIVK covers both pools, and `keys` holds up to 4 for `use_qsk` variants (4.2) | ZIP 229 and ZIP 326: one Orchard-protocol IVK trial-decrypts both pools, and it depends on `use_qsk` |
| Payment-push timing | Per-lease `alert_mode`, `instant` by default, with `private` batching into fixed-size scheduled pings; no cover pushes (5.2) | Push records can be obtained by court order; Apple's push budget and iOS's visible-push rule rule out decoys |
| OHTTP key consistency | Wallets fetch through two relays and require a match; the server publishes the config hash (3.2) | The IETF consistency drafts expired in 2024 without being standardized; the double-check approach needs no new infrastructure |
| Unlinkable payment (Privacy Pass, RFC 9576–9578) | Not adopted | Accounts are random tokens paid in shielded ZEC with no email, so payment is already unlinked from identity. The API also needs a stable per-account identity for push and leases, which defeats per-request unlinkable tokens. Revisit if card payments are ever added |
| Response size | Fixed 4096 bytes (3.3) | 16 KiB would mean 4× the server egress (about 1.7 TB a month at 10k users with 10% in the foreground) and the same load on volunteer relays |
| Self-host transport | OHTTP, or a Tor onion service for self-hosted servers only (3.1) | A single-user server has no crowd for OHTTP to hide in |

## 9. Open questions

1. **Relay software.** The Payjoin project's relay (now in the
   `payjoin/rust-payjoin` monorepo as part of `payjoin-mailroom`; the
   standalone `payjoin/ohttp-relay` was archived in December 2025) forwards
   only to gateways that declare the BIP77 purpose. Lantern Zero needs either
   an upstream change that makes accepted purposes configurable, or its own
   relay build.
2. **Finality depth.** The default of 10 is a placeholder. Set it once
   post-NU7 reorg behavior is known.
3. **Gateway admission for self-hosted servers.** 5.3 lets gateways accept
   only an allow-list of server keys. A gateway that does so can't wake
   phones for a self-hosted server. Proposed fix: bind each subscription to
   one server's VAPID key, the way Web Push binds a subscription to its
   `applicationServerKey`. The wallet reads the key from `info` and hands it
   to its gateway when it subscribes, and the gateway rejects pushes to that
   endpoint signed by any other key. This makes allow-lists unnecessary,
   and per-key rate limits stay. Cost: the gateway learns which server key
   each device uses, which for a self-hosted server points to one person.
   The gateway already sees that server's IP on every push.
